## Architecture

Read `docs/architecture.md` first (two nested loops; it is the v2 target design and gives a real status label per component), then `docs/core-rules.md`. Short version — components marked (S1)/(S2)/(S3) are **not in code yet**: don't assume they exist, and don't document commands for them until they do (plan: `docs/implementation-plan.md`).

- **Inner loop (gate, deterministic, blocks merge)**: `core/engine.py` runs plan → resolve → pick worker by capability → run → verdict → report. Policy comes from `configs/projects/_default.yaml` deep-merged (lists replace) with optional `<slug>.yaml`; the SUT's approved suites live in its own repo at `.qc-agent/suites/` and workers run with cwd = SUT root. Today every PR runs the whole policy; from S2 a `selector/` step picks the scope for `--trigger pr` (see Diff Agent below) and `core/` re-merges the floor.
- **Outer loop (LLM, advisory) = Ground-Truth Engine (S1, in progress)**: PRD → LLM emits test cases as JSON (never code) → deterministic render → PR `qc-agent/gt/<prd-id>` → QA flips `draft → approved` and adds edge cases (`origin: qa`). `.qc-agent/**` is locked by CODEOWNERS + branch protection and the gate runs only `approved` TCs; that is the only connection between the two loops. Today's code still has the older `scaffold/refine.py` / `integrations/refine_review.py` (non-blocking review suggestions).
- **Diff Agent (S2, design)**: for `--trigger pr`, Haiku 4.5 *chooses* workers from the policy allowlist; its only product is `selection.json` = floor (secrets + sast) ∪ rules(module-map) ∪ LLM. A diff touching `full_set_paths`, or any LLM failure, means FULL SET without an LLM call. `core/` re-merges the floor, so editing `selection.json` cannot drop it. `--trigger manual` takes an explicit worker list: no LLM, no floor.
- **Workers**: `workers/<name>.yaml` manifest + `src/qc_agent/adapters/<name>_adapter.py` (subclass `Adapter` in `_base.py`; only override `build_cmd` and `parse_output`) + optional `src/qc_agent/oracle/<kind>.py` registered with `@register`. Workers (e.g. schemathesis, k6, midscene, deepeval, playwright, semgrep, gitleaks, trivy, pytest (S1: runs generated Ground-Truth tests via JUnit); `workers/` has the full list) are spawned as subprocesses and speak the shared `schemas/task_spec.json` / `result.json` contract; capabilities are listed in `schemas/capabilities.json`. Adding a worker = adding files, never editing `core/`.
- **Service layer**: `api/` (FastAPI, `/api/v1`, also serves the static `web/` SPA — API is primary, web is just a client), `jobs/` (SQLAlchemy + Alembic models/migrations, `executor.py` runs jobs by shelling out to the CLI with cancel/timeout/env-lock/requeue), `auth/` (admin-invited users, argon2, lockout), `integrations/` (GitHub Check Runs/comments, webhook notify, CI ingest). `scaffold/` implements `init` (deterministic scanner + templates) and `init --refine`. Target from S3: the PR and manual flows must not depend on `QC_DATABASE_URL`; only the service (dashboard/executor) needs Postgres.
- One Docker image serves CLI, API and executor (`Dockerfile`); `Dockerfile.ui.tmpl` is for SPA SUTs.

## Hard rules (from docs/core-rules.md)

- No LLM calls and no `if worker == ...` in `core/`, and no top-level import of `qc_agent.llm` / `groundtruth` / `selector` there (new CLI commands use lazy imports, like `init`/`validate`/`doctor`); per-worker differences belong in manifest/adapter/oracle. LLMs may appear in exactly three places: workers (non-blocking findings only), `groundtruth/` (output is a file reviewed via PR), `selector/` (only output is `selection.json`; the floor is non-negotiable and merged twice). An LLM never issues the verdict.
- No worker-specific fields in the shared schemas.
- Retry only `error` (infra), once. Never retry `fail`.
- Do not edit contract files (`schemas/task_spec.json`, `schemas/result.json`, `workers/_template.yaml`) outside the SemVer process guarded by `schemas/CONTRACT.lock`, `tools/freeze_contract.py` and the `contract-check` workflow (reviewers: `.github/contract-reviewers.yaml`).
- Severity v2 (S3, not in code yet): `severity_hint` ∈ low/medium/critical (contract 2.0.0); verdict `BLOCKED` (critical/medium, or a gate task error/skip) / `PASSED_WITH_WARNINGS` (Low only) / `PASSED`. Until S3 the code still uses low/medium/high and `FAIL > YELLOW > PASS`.
- Logs are structured JSON on stderr and must never include spec/inputs content, PRD/diff/prompt/LLM-response content, or secrets (`logging_setup.py`); off-machine data flow is recorded per worker-declared `data_egress` in `runs/<job>/egress.jsonl`. Record egress **before** every LLM/Jira call (`core/egress.record`); on `deny`, send nothing.
- PR/PRD/diff/SUT data is untrusted: delimit it in prompts, force LLM output into schema + enum allowlist, sanitize before Markdown, never pass it to a shell or embed it in generated code. The gate never goes red because of an LLM, cost or Jira failure (LLM failure → FULL SET; Jira/GitHub failure → warning only).
- In plan YAML, quote the retry key `"on":` (bare `on` parses as `True`).
- Run from the repo root: adapters are spawned with `python -m` and plan paths are relative. Base images and GitHub Actions are pinned by digest/SHA; keep them pinned.
